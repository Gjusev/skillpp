# skillpp × skill-issue — routing vs task performance (ROADMAP item 5, first slice)

Generated by `scripts/skill_issue_demo.py`, executed by
[skill-issue](https://github.com/Gjusev/skill-issue) (Claude Code 2.1.322
headless, model `sonnet`, 1 repetition per cell). Task: "explain query.sql
with the relevant installed skill" — the verifier passes only if the agent
followed sql-explainer's prescription (EXPLANATION.md, ≥3 `## Step N`
sections, `skill-used` marker). The workspace pre-installs sql-optimizer
(the near-duplicate); skill-issue installs sql-explainer with draft or
refined metadata (skillpp MetadataRewriter, glm-5.3-flash).

Result: **no routing failure to fix** — the LLM agent picked the right skill
under draft and refined metadata alike, at equal cost (n=1 per cell;
skill-issue's own report labels this "insufficient evidence for superiority
claims"). Consistent with the router matrix: interference lives in
lexical/similarity routers, not in the LLM routing that drives real agents.

Two mechanism findings surfaced while building it:

1. **Name leakage**: with descriptive skill names the metadata axis cannot
   bind — names alone disambiguate. Neutral names (`sql-tool-1/2`) are
   required to test description-driven routing at all.
2. **Garbage-in, garbage-out refinement**: feeding the rewriter a draft that
   is a verbatim copy of the predecessor's description produced a polished
   WRONG refinement — an optimizer description for an explainer skill. The
   rewriter never sees the skill body, so an untruthful draft yields
   confident untruthful metadata. The paper's implicit assumption (drafts
   are sloppy but truthful) is load-bearing.

full run artifacts under `runs/` (untracked).
